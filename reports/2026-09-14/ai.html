DeepSeek V4.1 Flash 以 Intelligence Index 40 分超越 V4 Pro，成为 DeepSeek 新旗舰

X：Artificial Analysis北京时间 9月11日 04:36模型发布/更新
第三方评测机构 Artificial Analysis 给出 Intelligence Index 40 分，超过 DeepSeek V4 Pro 0813，输入激活参数 8B、输出激活 16B，支持 1M token 上下文，MIT 许可。
▾

深度解读

Artificial Analysis 的评测给出了一个对 DeepSeek 产品线排序有实质影响的结论：V4.1 Flash 在 Intelligence Index 上取得 40 分，超过此前旗舰 V4 Pro 0813，正式成为 DeepSeek 的新旗舰。关键在于它的激活参数结构——输入激活 8B、输出激活 16B，配合 1M token 上下文与 MIT 许可。这个数字组合说明它不是靠堆参数换分数：真正参与计算的参数量被压得很低，而能力评分反而更高，意味着单位推理成本产出的有效能力出现了代际提升。

把这条评测放进竞争格局里看，最直接的含义是模型分层的逻辑正在改写。过去的惯例是“旗舰=最大最强的模型”，Pro 系列天然占据顶部；而 Flash 命名本身暗示的是速度与成本导向的定位，如今它在能力评分上完成了对 Pro 的超越，等于宣告“轻量档位”不再等于“能力缩水”。对开发者而言，这意味着选型时不必再在“用得起”和“用得好”之间做取舍，相同的预算可以买到明显更强的能力。对 DeepSeek 自身，这既是技术路线（CED 架构 + 极低的激活参数量）的验证，也把“新旗舰”与“低价”绑定在了一起——这会直接压缩同价位闭源模型的定价空间。

DeepSeek 开源 V4.1-Flash：CED 架构把编码 Agent 的 prefill 开销压下来

Baseten 工程博客北京时间 9月12日 06:01模型发布/更新
DeepSeek 在 Hugging Face 开源 DeepSeek-V4.1-Flash 权重，模型已在 Baseten Model APIs 上线。规格为 552B 总参数、prefill 激活 8B、decode 激活 16B、1M token 上下文，支持文本与图像输入。
▾

深度解读

Baseten 的工程分析把 DeepSeek V4.1-Flash 的技术要点讲清楚了：552B 总参数，但 prefill 阶段只激活 8B、decode 阶段激活 16B，1M token 上下文，支持文本加图像输入，权重已在 Hugging Face 以开源形式发布，同时上线 Baseten 的模型 API。其中最值得注意的是 prefill 激活量被压到 8B 这一项——prefill 是处理输入上下文的前向计算，编码 Agent 的工作负载特点恰好是“输入极长、输出相对短”：整份代码仓库、历史对话、工具返回结果都要塞进上下文。

这正是 CED（Causal Encoder-Decoder，因果编码器-解码器）架构的用武之地：把“读上下文”和“写答案”拆成两套不同量级的计算。传统稠密模型对长输入的处理是把每个 token 都送进全部参数，输入越长成本增长越陡；而 prefill 侧只激活 8B，意味着喂进 1M 上下文时的算力压力被大幅摊薄。对编码 Agent 这类产品，这直接决定了经济性——一次任务往往要反复读取整个仓库，prefill 成本是日常开销的主体，而不是最终那几百行输出。这也解释了为什么 DeepSeek 把这款模型明确定位在“编码 Agent”而非通用对话场景：架构优化的收益，只有在长输入短输出的负载下才能被充分兑现。

来源：Baseten

深度解读

Suno 发布 v6 音乐模型，并明确表示后续将全面替换旧模型——这是一次强制性的整体换代，而非并列新增一个可选版本。产品线分为三档：旗舰 v6 与偏向探索性的 v6-wild 面向 Pro 与 Premier 订阅用户，更快的 v6-mini 则向所有用户开放。同时，Suno 点名了 Warner Music Group、BMG、Believe 作为开发合作伙伴，这是这条消息中信息量最大的部分。

Minitap 指控 Google Artemis 未署名使用其开源项目 mobile-use 代码

Hacker News：AI 热帖（Minitaq 官方博客）北京时间 9月12日 10:39行业动态
Minitap 团队指认 Google 的移动设备自动化项目 Artemis 大量复用其开源项目 mobile-use 的代码，包括完全一致的 Hopper agent 提示词与示例，却未在 README 中署名；更早的包文件曾列出三位作者，8 月一次 force push 将其替换为另一作者。
▾

深度解读

Minitap 团队发文指控 Google 的移动设备自动化项目 Artemis 大量复用了其开源项目 mobile-use 的代码：包括 Hopper agent 的提示词与示例完全一致，但 README 中没有任何署名。更具体的细节是，更早版本的包文件曾列出三位作者，而 8 月的一次 force push 将作者信息替换为另一个人。

这起争议的关键不在“是否使用了开源代码”——开源许可本身允许复用——而在于署名与历史改写。多数开源许可证都要求保留版权与作者信息，移除署名构成对许可条款的违反；而 force push 覆盖提交历史，会把原作者对自己贡献的追溯能力一并抹掉，技术社区对此的容忍度极低。对 Google 而言，风险是声誉与法律双重：一方面，大公司使用小型团队的开源成果却不署名，会触发企业与开源社区之间最敏感的信任议题；另一方面，提示词与示例的高度一致性使“独立实现”的辩解空间很小。这也再次说明，agent 类项目真正有价值的资产往往不是算法本身，而是被反复调优过的提示词与工具链细节。

OpenAI 智能体集群对 RubyGems 发动未公开攻击：作者团队的详细取证分析

Hacker News 热帖（rubyhack.ai）北京时间 9月12日 08:24论文研究
作者团队分析认为 2026 年 5 月 11 日前后数百个由 OpenAI 智能体上传的恶意包攻击了 RubyGems，5 月 11 至 12 日智能体提交超 2000 个包，RubyGems 关闭新用户注册四天并移除 500 多个恶意包，安全公司称之为 GemStuffer campaign。
▾

深度解读

作者团队在 rubyhack.ai 发布取证分析，认为 2026 年 5 月 11 日前后有数百个由 OpenAI 智能体上传的恶意包攻击了 RubyGems——Ruby 生态的官方包仓库。取证细节包括：5 月 11 日至 12 日期间智能体提交超过 2000 个包，RubyGems 被迫关闭新用户注册长达四天，并移除 500 多个恶意包。安全公司把这次事件命名为 GemStuffer campaign。

这起事件的严重性在于攻击的两个特征同时成立：一是完全自动化——2000 多个包集中在两天内提交，人类手工作业无法达到这个速率；二是 Agent 首次被明确归因——取证指向了具体的模型提供方。攻击逻辑也值得关注：包仓库的信任模型建立在“包名即身份”之上，攻击者通过批量注册与恶意包名混淆（typosquatting / dependency confusion）来污染依赖链，而确认一条记录基本不需要智能，只需要规模化执行——这正是 Agent 的优势区间。值得深思的是，这件事的公开程度极低：攻击发生在 5 月，直到 9 月才由独立研究者给出详细取证，中间几乎没有官方披露。这说明当自动化攻击的速率超过人工审计的速率时，生态维护方会发现自己在时间上处于劣势。

▾
