Thinking Machines 发布 Inkling 2 Small，计划开放 5940 亿参数权重

Thinking Machines Lab时间不详模型发布/更新
混合专家模型每次激活 170 亿参数，权重计划在外部安全测试后以 Apache 2.0 开放。
▾

深度解读

Thinking Machines Lab 于十一月五日发布 Inkling 2 Small：模型总参数五千九百四十亿，每次激活一百七十亿，视觉编码器有二点九二亿参数，预训练使用八点四万亿 token。扩展推理阶段支持最长一百万 token 的轨迹，目前通过 Tinker 使用，每项任务标价一点一八美元。

混合专家架构让模型拥有较大的总参数容量，同时每次生成只调用其中一部分；但权重存储、专家调度和推理轨迹仍会占用计算资源。百万 token 指的是扩展推理轨迹，不能直接等同于用户每次输入都能获得同样长度的有效上下文，也不能单靠总参数比较模型质量。

对 Thinking Machines 的开发者，下一步的关键是外部安全测试后实际开放的 Apache 二点零权重及其部署条件；现阶段 Tinker 的任务价格不等于自托管成本。该公司所称下周开放仍是计划，直到权重发布并由第三方检验，硬件需求与真实任务效果都不能视为已经确定。视觉编码器的加入也使图像输入成为模型结构的一部分，但图像理解效果仍需具体测试。

来源：Thinking Machines Lab

OpenAI 推出 GPT-6 Cyber，专攻漏洞发现与利用研究

VentureBeat时间不详模型发布/更新
第三方 EnterpriseBench-CoreCraft 得分 71.8%，Cisco 和 Mozilla 已参与使用。
▾

深度解读

OpenAI 十一月五日推出面向漏洞发现与利用研究的 GPT-6 Cyber，称其更可靠地遵守安全容器边界。Surge AI 的第三方 EnterpriseBench-CoreCraft 测试给出百分之七十一点八的成绩；Cisco 与 Mozilla 团队已经使用该模型。此前公布的 Linux 内核研究也由这一模型驱动，报告发现九百四十八种攻击方式。

漏洞研究需要在有限权限环境中观察系统行为，再判断异常是否构成可利用的问题。模型在基准和内核研究中的表现说明它能参与复杂安全工作，但九百四十八种攻击方式并不等于同等数量已确认的独立漏洞，更不能推断任意企业环境具有相同风险。容器边界的可靠性也需要按具体工具权限检验。

对 Cisco 和 Mozilla 的安全团队，专门模型可能加快已授权代码审计和复现工作，但仍需人工确认影响与修复。报道指出其接口价格高于 Anthropic 和 Google 的竞争产品，采购比较应同时计算每次有效发现的成本；百分之七十一点八只是所列基准的成绩，不保证在私有代码或生产系统上达到同一水平。

来源：VentureBeat

百度开放 ERNIE 5.5 Flash Base，先提供基础模型权重

The Neuron时间不详模型发布/更新
模型总参数 2800 亿，每个 token 激活 140 亿，采用先发布基础模型的路线。
▾

深度解读

百度发布开放权重模型 ERNIE 5.5 Flash Base，总参数为二千八百亿，每个 token 激活约一百四十亿。此次先提供基础模型，而不是先推出已经针对对话指令完成微调的版本；开发者可以在这一基础上选择自己的训练数据与后续适配方式。

基础模型保留了面向不同用途继续训练的空间，但不会因为名字中有 Flash 就自动适合所有对话任务。混合专家的活跃参数量低于总量，可减少每一步计算涉及的参数；同时部署方仍要考虑全部权重的存储，以及专家在设备之间如何分配。二千八百亿和一百四十亿分别回答容量与单步计算的不同问题。

对百度生态的企业开发者，这一发布提供了定制领域模型的起点，例如在自有材料上进行指令适配；实际效果取决于训练数据和验证集。现有资料没有给出足以横向比较的独立任务成绩，也没有证明基础版本开箱即可满足企业安全要求，因此上线前需要自行评估输出、资源占用和许可条款。

AI Briefs时间不详模型发布/更新
模型支持文本、图像和视频，输入价格为每百万 token 0.15 美元。
▾

深度解读

MiniMax 发布面向智能体的 M3.1 Flash，采用四千二百八十亿总参数的混合专家架构，每次约激活二百三十亿参数，并提供一百万 token 的上下文。模型原生支持文本、图像与视频输入，公布的输入价格为每百万 token 零点一五美元。

智能体处理长文档或视频时，长上下文可以让更多材料进入同一次工作，但能容纳材料并不等于能准确检索所有细节。混合专家设计也把总模型容量与每次激活的计算量分开；输入单价只是费用的一部分，多轮调用、输出长度和视频处理方式都可能影响最终账单。

对于使用 MiniMax 构建跨文本与视觉流程的团队，低输入报价适合拿自己的长任务做成本试算，并把信息遗漏与响应时间一并测量。资料没有给出覆盖各类视频任务的独立对照成绩，也没有给出完整输出计费条件；因此不能仅凭百万上下文或输入单价断言它比其他服务更便宜、更准确。

OpenAI 将 Images 2.6 拆为 Flare 与 Sunburst 两种图像模型

AI Tools Recap时间不详产品发布/更新
Flare 侧重速度和草稿，Sunburst 侧重质量及多次编辑一致性。
▾

深度解读

OpenAI 在十一月四日发布的 Images 二点六接口中区分 Flare 与 Sunburst：前者面向较快的图像生成与草稿，后者着重最终质量，以及对同一图像进行多轮修改时保持内容一致。两个名称对应不同取舍，应用开发者可以按制作环节选择调用。

在设计工作流中，最初探索构图时可能需要快速尝试多个方向，最终定稿却更关注细节与反复修改后主体是否走样。把速度和一致性拆开，有助于开发者为不同步骤设置模型，而不必让每次草图都承担高质量生成的等待时间。具体收益仍取决于提示、图像内容和编辑次数。

对使用 OpenAI 接口的设计工具，合理测试是用同一组素材分别记录草稿生成速度、迭代后的主体变化及费用，再决定何时从 Flare 切到 Sunburst。现有资料没有提供两个模型的完整价格或独立一致性测评，因此不能把产品定位直接当成所有图像任务的性能保证。图像服务商还应测量同一角色在多次修改中的外观变化，避免草稿和定稿之间出现难以察觉的偏差。

来源：AI Tools Recap

AI Tools Recap时间不详产品发布/更新

▾

深度解读

Google 正式发布 Gemini Omni 一点二 Flash，单段视频最长十五秒，上一版上限为十秒。七百二十像素视频价格为每秒零点零七美元，较 Omni 一点一下降百分之三十；用户还可先以三百六十或七百二十像素制作草稿，再提升到一千零八十像素或四千像素。

十五秒上限比十秒多出一半，可在同一片段中容纳更长的动作或镜头；先用低分辨率试构图，再对选中的片段提升分辨率，也能减少反复生成高分辨率废稿的次数。以公布的七百二十像素单价计算，满十五秒的基础生成价格为一点零五美元，未计其他可能费用。

对 Google 的视频工具用户，价格下降与更长片段都有助于比较不同制作方案，但草稿升频能否维持人物、动作和文字的连贯性，仍要用自己的素材检验。一点零五美元只按所列单价乘长度计算，不包含未披露的升级费用，也不能说明最终合格片段需要生成多少次。

Google ADK 2.14 将 A2A 协议和核心运行时标记为稳定

AI Tools Recap时间不详产品发布/更新
Agent-to-Agent、执行环境与核心运行时一同进入稳定状态。
▾

深度解读

Google 的 Agent Development Kit 二点十四点零版本将智能体之间通信的 A2A 协议标记为稳定，执行环境和核心运行时也一并转入稳定状态。此举面向用多个智能体共同处理任务的开发者，为组件之间交换工作和结果提供更明确的版本信号。

多智能体系统常把任务拆分给不同服务：一个负责接收请求，另一个执行专门工作，结果再返回原流程。通信协议的稳定有助于降低接口频繁变化带来的维护负担，但协议本身不决定各智能体是否可信，也不保证不同实现对任务状态、权限或失败重试的处理完全一致。

对于依赖 Google ADK 编排服务的团队，升级前可以用现有任务检查智能体发现、消息传递和异常恢复是否符合预期，并确认调用方能否识别远端身份。稳定标签说明该版本进入新的维护阶段，不能推断所有第三方智能体已实现互通，也不能替代跨组织授权与数据访问控制。

Claude Code 将 MCP 工具调用移入后台执行

AI Tools Recap时间不详产品发布/更新

▾

深度解读

据 AI Tools Recap 汇总，Claude Code 调整模型上下文协议工具调用的执行方式，将这类调用移到后台，使耗时较长的工具不再占住主循环。更新针对的是编码助手等待外部工具结果的过程，而不是声称所有工具执行本身都变快。

编码任务可能同时需要读取资料、等待远端服务返回和继续处理其他工作。若主循环必须等待一个慢工具完成，后续可独立执行的步骤就会排队；后台处理可以减少这种等待对交互的阻塞。但依赖工具结果的操作仍必须等结果到达，任务之间的先后关系不会因异步执行自动消失。

对 Anthropic 的 Claude Code 用户，使用长耗时工具时可观察界面响应和任务完成顺序，并确保后续修改没有误用尚未返回的信息。现有摘要没有给出具体版本、耗时改善幅度或所有工具兼容情况，因此这项更新不能被解读为每种任务都会加速，也不能省略对后台失败结果的检查。

来源：AI Tools Recap

xAI 为七个 Grok API 模型默认启用隐形文本水印

Data Studios时间不详产品发布/更新
十一月七日起覆盖 Grok 4.7、4.6、4.5、4.3 和三个 4.20 变体。
▾

深度解读

xAI 自十一月七日起在 Grok API 默认启用隐形文本水印，覆盖 Grok 四点七、四点六、四点五、四点三以及三个四点二零变体，共七个模型。报道将这一安排与欧盟人工智能法案的时间表联系起来，涉及的是接口生成的文本标记。

隐形水印旨在为识别机器生成文本提供线索，而不是在肉眼可见的每段内容上添加声明。其实际识别能力取决于文本长度、后续编辑和检测方法；复制、翻译或改写可能改变检测条件，因此默认启用并不意味着所有传播出去的文本都能被可靠识别。

使用 Grok API 的出版或企业应用应检查水印对自身文本处理与来源标注流程的影响，同时考虑误报和漏报。七个型号的覆盖范围不等于所有 xAI 产品或所有历史文本都已标记；这则报道也未证明水印在任意语言、短句和大幅改写之后仍能稳定检测。对需要保留出处的应用，水印只是机器可检测的信号，用户可见的来源记录仍有独立用途。

来源：Data Studios

银行交易数据能够帮助助手按账目解释支出或整理记录，但即使不能发起付款，账户余额与消费明细仍高度敏感。用户授权、账户连接和云端处理构成一条完整的数据路径；只读限制降低了直接移动资金的权限，却不能消除错误解读交易或不当暴露个人信息的风险。
